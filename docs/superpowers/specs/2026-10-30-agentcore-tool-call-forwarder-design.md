# AgentCore tool-call preflight: blocking tool calls and their results

**Date:** 2026-10-30
**Status:** Implemented by `agent-core/` (package `slashid-ai-forwarder-agentcore`). The live run of 2026-11-03 showed production accepting these preflights (HTTP 200) and AgentCore accepting the allow and deny shapes; section 6 lists what is still unconfirmed.
**Evidence:** `docs/agentcore/agentcore-findings.md` (what AgentCore exposes and what we measured). Its Harness lifecycle hooks and Gateway interceptors are called Harness hooks and Gateway hooks here.
**Event types:** none in v1. The `event_type` field is a separate, later design. v1 sends no `event_type`; everything arrives at `/preflight`, and the server builds a verdict from the tools and `accessed_files` the event carries, which is enough for now.
**Precedents followed:** Codex hooks (`2026-09-30-codex-hooks-design.md`, `2026-10-13-codex-tool-calls-design.md`) and `anthropic/src/slashid_anthropic_forwarder/hook/toolcall.py` and `hook/verdict.py`.

## 1. Scope

**Goal.** For agents on AgentCore, ask SlashID before each tool call runs and before its result reaches the model, and block on a deny (for a Harness tool's result, a deny stops the run instead; section 3.1). v1 is preflight only: no events are pushed. The existing forwarders report tool use inside the `model_call` event they push for each model response, and AgentCore gives us no model call to carry it.

**Surfaces.** Harness hooks (the Harness lifecycle hooks `before_tool_call` and `after_tool_call`) and Gateway hooks (the Gateway's REQUEST and RESPONSE interceptors on `tools/call`, MCP shape), served by one Lambda function (section 3). One workspace member, `agent-core/`, builds the package. Both surfaces call a single `tool_call` module in `agent-core/` (tool resolution, the extractor calls, event building, the preflight call and the deny text) over `shared/` (section 4.3), so they cannot disagree about what a preflight is.

| Agent shape | Covered |
| --- | --- |
| Harness | every tool type is checked by Harness hooks (builtin, Gateway, remote MCP and inline tools; the managed Browser and Code Interpreter tools are untested), though file references are extracted only for recognized connector tools (section 4.1); Gateway tools additionally by Gateway hooks |
| Runtime | tools behind a Gateway only, by Gateway hooks |

**Out of scope.** Pushing events for tool calls or agent runs; model calls and prompts as sent (the `bedrock/` forwarder and optional traces keep that); checking the user's prompt (`before_invocation`); tools defined inside a Runtime agent's code; tool calls that bypass a Gateway on a Runtime agent; identity from a JWT's `iss` and `sub` (v2; the token is never read, so a JWT-authorized Gateway is checked like any other); managing Policy engines; automation that attaches hooks or interceptors across an account; chaining behind a customer's own Gateway interceptor (follow-up).

**Real Drive.** Google's Drive MCP server needs 3-legged OAuth, which AgentCore supports only behind JWT-authorized Gateways. The interceptors do not read the token, so such a Gateway is checked like an IAM one, and the real Drive server is covered through it, untested. The Harness hooks cover it when a Harness calls it directly, also untested. The Drive call and result shapes the extractors rely on come from the IAM stand-in Lambda, which mirrors the real server's schema and a captured result; only the tool names and schemas were captured from the real server.

**What is sent.** The request and call ids, a timestamp, the session id as `conversation_id`, the `User-Agent` (Gateway only), the agent, role and Gateway identity, the tool name and server, and for recognized connector calls the file references, names, media types and sizes, and a content hash where a download result carries the bytes. Not sent: which model ran, the prompt, the model's output, and tool arguments and results.

## 2. Checks

A call check is made before a tool runs; a result check, before its result reaches the model. All are preflights. Result checks are part of the base flow, not a separate switch (the per-surface switches and shadow mode in section 3.3 still apply).

| Check | Surface and trigger | Verdict |
| --- | --- | --- |
| call check | Harness hooks: `before_tool_call`; Gateway hooks: REQUEST on `tools/call` | applied |
| result check | Gateway hooks: RESPONSE on `tools/call` | applied |
| result check | Harness hooks: `after_tool_call` | applied as a stop (it does not withhold the result) |

Nothing else is sent: `before_invocation`, `after_invocation`, `initialize`, `tools/list` and notifications such as `notifications/initialized` pass through (a RESPONSE to a notification has no body, and any RESPONSE to a request that is not a `tools/call` is echoed unchecked).

**Order of one call:** Harness `before_tool_call`, Gateway REQUEST, AgentCore Policy (when attached), the target, Gateway RESPONSE, Harness `after_tool_call` (every call in our captures). A Harness `before_tool_call` deny means the Gateway is never reached. A Gateway REQUEST or Policy deny skips the target, but the RESPONSE and `after_tool_call` still fire, carrying the deny text. `after_tool_call` also fires after a denied `before_tool_call`, with `status: error` and the deny text, and nothing marks who denied. Every deny text we apply ends with a short HMAC reference (section 3.1), so a result check recognizes our own: a result that is exactly one text block, with no `structuredContent` and no other content, whose reference verifies, whatever its error flag, is answered allow without calling SlashID, on either surface and whichever container the call landed on. The reference covers the text before it, so a tool cannot dress its own content as a deny; the most a replay of a captured deny can do is skip the check of that same short text. Other error results are still checked, with `used_tools` and `is_error` and no `accessed_files`; `connector_files` returns the input's reference even for an error, so the module drops `accessed_files` for error results itself.

**Two surfaces, one call.** On a Harness with Gateway tools both surfaces fire for the same call: two call checks and two result checks, up to four serial checks each bounded by the budget (section 3.3), each in its own hook timeout; a server that is slow but reachable can cost 4 × the budget per call (14 s at the default, plus up to 1 s per cold role lookup), and v1 has no circuit breaker. Either that denies blocks the call, and the Gateway hooks report the caller's role, which the Harness hooks must look up. We accept the extra round trip and do not de-duplicate: the surfaces share no call id (`toolUseId` is invisible to the Gateway, and the trace id is one per invocation, not per call), and the two invocations may land on different containers. An environment where it is not worth it turns one surface off (section 3.3). Each surface pairs its own call and result checks: the Harness by `toolUseId`, including the two requests of an inline function; the Gateway by `REQUEST_ID`. We send the ids and the order; the pairing itself is the server's.

## 3. Behavior

### 3.1 How a deny is applied

| Surface | Check | Applied as |
| --- | --- | --- |
| Harness hooks: `before_tool_call` | call check | `{"decision":"deny","reason":...}`; the call is skipped and the model receives the reason as the tool result |
| Harness hooks: `after_tool_call` | result check | `{"decision":"deny","reason":...}`; the run stops (`hook_stopped`) but the result stays in the session and reaches the model on the next request (tested), so this stops the agent without withholding the result |
| Gateway hooks: REQUEST | call check | `transformedGatewayResponse` with `statusCode` 200 and body `{"jsonrpc":"2.0","id":<request id>,"result":{"isError":true,"content":[{"type":"text","text":reason}]}}`; the tool is not called |
| Gateway hooks: RESPONSE | result check | the same `transformedGatewayResponse` shape, `isError` true like the REQUEST deny, with the text `Content withheld: <reasons>` and the reference (replacing a result is captured; the flag is set by a fixture test); the model sees only the notice |

Every deny text is the reason followed by a reference, and every Gateway deny sets `isError` true (the Harness needs no flag: AgentCore records a denied `before_tool_call` as `status: error`). Several deny reasons are joined as the Anthropic hook does (`join_deny_reasons`, moved to `shared/`; it joins with "; " and drops a closing "." from all but the last reason), and the reason text is capped at 500 characters, the Anthropic hook's bound (chosen, not an AgentCore limit), counting any fixed prefix such as `Content withheld: ` and not the reference, which is computed over the capped text. Allow is `{"decision":"allow","reason":"slashid"}` for the Harness. For the Gateway it is the request or response echoed back from the raw payload (held as `JsonValue`; our models read views of it and allow extra fields), not rebuilt from them, so fields we do not know (`_meta`, headers) survive: `transformedGatewayRequest` with the body on REQUEST and `transformedGatewayResponse` with the status code, headers and body on RESPONSE (headers included whenever the payload carries them; the Gateway accepted that echo for every message of a full session, including the body-less response to a notification, and section 6 asks only about an echo with no headers); section 6 asks whether an empty `mcp` object is accepted, which would avoid echoing large bodies such as `tools/list`.

**The reference.** A deny text ends with ` (ref <12 hex>)`: lower-case hex of the first 6 bytes of HMAC-SHA256 over the text before the space, checked by anchoring ` \(ref ([0-9a-f]{12})\)$` at the end of the text. The key is derived from the push token (HMAC of a fixed label), so every container of one connection computes the same reference with no shared state; rotating the token makes older denies verify no more, and a deny that does not verify is simply checked like any result. The reference is visible, so the model may repeat it to the user, which is harmless and works as a support reference. A hop that rewrites a result's text costs one extra check of our own deny, never a missed one. The reference survived the Harness `before_tool_call` to `after_tool_call` hop and the Gateway REQUEST to RESPONSE hop in the live run; section 6 lists the hops not yet seen.

The Gateway RESPONSE is where a result is replaced, and it checks every result, not only the read tools: a `search_files` result carried a `contentSnippet` of the tagged file and the model quoted it even with the read redacted. Every `tools/call` RESPONSE gets a result check except our own notices (section 2), including an error result, a Policy denial (`-32002`) and a result with no file reference, since the server records preflights and a skip would leave gaps. The Harness `after_tool_call` is the only result-side signal for tools that bypass a Gateway (`shell`, `remote_mcp`, inline functions).

### 3.2 One function

One Lambda function serves both surfaces. The entry point dispatches on the payload: a top-level `event` field is a Harness hook; `interceptorInputVersion` with an `mcp` key is a Gateway hook (an `http` key is a pass-through, rule 2). Two thin adapters translate each payload and answer, and everything else (tool resolution, extractors, event builder, preflight client, deny text) is shared. The adapters stay separate so the package can be split into two functions later; sharing costs one concurrency pool and timeout, and one bad release breaks both surfaces.

Rules, in order:
1. **Dispatch.** The surface switches (section 3.3) apply as soon as the surface is known from its discriminator, before the rest of this rule, so an operator's off switch also silences a format-change deny. A top-level `event` field marks a Harness hook; `interceptorInputVersion` a Gateway hook, and a `gatewayResponse` that is present and null marks a REQUEST, present and non-null a RESPONSE. A payload with no discriminator and none of the keys `mcp`, `http`, `gatewayRequest` or `context` is not ours: it is answered allow and logged with its top-level keys only, never the payload, as a `pass_through` line with reason `unknown_payload`. Any other payload we cannot place (both discriminators, an `interceptorInputVersion` other than `1.0`, neither `mcp` nor `http`, an absent `gatewayResponse`, a Harness `event` other than `before_invocation`, `after_invocation`, `before_tool_call` and `after_tool_call`, or one of those keys without a discriminator) is an AWS format change, not a caller's choice, and takes the no-answer path (section 3.3), so it follows the configured fail mode instead of silently failing open. The real format being unknown, the answer is the best the 1.0 shapes allow: allow is the 1.0 echo of the request or response the payload carries, else an empty `mcp` object; deny is a `transformedGatewayResponse` with a JSON-RPC result of `id` null and the policy-unavailable text (Gateway) or `{"decision":"deny",...}` (Harness). Neither is tested (section 6), and with `deny` such a payload may block `initialize` and `tools/list` too, which is what the setting means.
2. **Pass-through, without calling SlashID:** an `http`-shape payload, answered `{"interceptorOutputVersion":"1.0","http":{}}`; any MCP message other than `tools/call`, echoed; a Harness `before_invocation` or `after_invocation`, answered allow; a RESPONSE flagged `isStreamingResponse` (untested, section 6), echoed. The `Authorization` header (a JWT or a SigV4 signature) is never read: a `tools/call` is checked whatever authorizer the Gateway uses. A `tools/call` is identified by the client context's `GATEWAY_ARN` (set by AWS), so a JWT Gateway call with no `awsPrincipalArn` is still checked; one with neither cannot be sent and takes the no-answer path (section 3.3). Every skip that echoes a `tools/call` unchecked writes a `pass_through` log line (surface, reason) a customer can alert on, beside the `fail_mode` line of section 3.3.
3. **Parse.** The envelope of a `before_tool_call` or `tools/call` (a non-empty tool name and the ids) must validate; the tool input and result inside it are free-form JSON handed to the extractors, so a shape they do not know, a truncated one (`{truncated, preview}`) included, gives no file references and is not a parse failure (a `truncated_input` log line records a `{truncated, preview}` tool input, since a call padded past 64 KiB would otherwise lose its references unnoticed; the README states the limit). If the envelope does not validate, the call cannot be checked and is denied regardless of the fail mode, on both surfaces (logged and allowed in shadow mode): the fail mode is for SlashID being unavailable, not for a caller choosing what we can read. A `before_tool_call` that no longer carries the tool name and ids is an unreadable envelope too and is denied the same way (an event name or version we do not know is rule 1's, and takes the fail mode: the first is a payload we can read and a caller shaped, the second a format we cannot place); the `fail_mode` log line makes both visible. This covers a JSON-RPC batch containing a `tools/call` (MCP `2025-03-26` allows batches; checking each element is deferred, and a batch without one is echoed). A Gateway deny to a batch or to a request whose `id` cannot be read or is absent (a notification) is one JSON-RPC result with `id` null (batches were not captured, section 6). An `after_tool_call` or RESPONSE whose envelope does not validate takes the no-answer path (section 3.3), and so does a RESPONSE whose `gatewayRequest` is null: there is no tool name to check (reason `no_request`; whether the MCP RESPONSE does this is unconfirmed, section 6). A result with no `result`, or whose content has no readable payload, is not a parse failure: it gives no file references.
4. **Exceptions.** Any other exception in our code is caught at the entry point, logged without the payload (an `unexpected_error` line with the exception's type name only), and answered as a check that gave no answer (section 3.3). A `RecursionError` (a payload nested too deep to read) is the exception: it is denied whatever the fail mode, like an unreadable envelope. An exception from the configuration (a missing push token) escapes as a Lambda error, which AWS's `failureMode` decides. A missing `REQUEST_ID` in the Lambda client context is not an error: a random UUID stands in, the pairing of that call's checks is lost, and it is logged. A tool name with no `___` is a bare tool and gets `resolve_tool`'s default server (`builtin`).

The handler runs one event loop for the life of the container, with one `httpx.AsyncClient` and the caches in a container-level runtime object, so a warm invocation reuses its TLS connection and the cache. This differs from `bedrock/handler.py`, which calls `asyncio.run` per invocation. A connection pooled before a Lambda freeze may be dead when the next invocation thaws it, and `preflight_invocation` does not retry, which would turn the first call after idle into a fail-mode outcome. So the module records the wall-clock time of its last request and starts the next one on a fresh client when more than 4 s have passed (httpx's own keepalive expiry is monotonic and may not advance during a freeze), and retries a call once on a new connection after a transport error (not after a timeout or an HTTP status), with the remaining budget as the request timeout; a preflight can therefore reach the server twice, which it records as two. The first call after idle is tested (section 5). `GetHarness` and `GetGateway` go through an `aiobotocore` `bedrock-agentcore-control` client in the Lambda's own region (not the ARN's), created once per container, with its own connect and read timeouts (0.5 s each), a ceiling of 1 s on one lookup in all (a constant, enforced around the call too) and no retries.

### 3.3 Configuration

All settings use the `SLASHID_` prefix, as in the other forwarders. The fail mode, budget and shadow mode live in this package's config, as in the Anthropic hook (Codex has its own copy, with a `deny` default and no shadow mode); moving them into shared is a follow-up. The push token is an environment variable set from a CloudFormation parameter, as in `bedrock/`.

| Setting | Default | Meaning |
| --- | --- | --- |
| `SLASHID_HARNESS_HOOKS_ENABLED` | `true` | when false the Harness adapter answers allow without calling SlashID |
| `SLASHID_GATEWAY_HOOKS_ENABLED` | `true` | when false the Gateway adapter echoes the request or response |
| `SLASHID_VERDICT_FAIL_MODE` | `allow` | `allow` or `deny`, as in the Anthropic hook |
| `SLASHID_VERDICT_BUDGET_MS` | `3500` | bound on one check (100 to 6500). The role lookups run before the budget starts and can take up to 1 s each (2 s on a Gateway call that claims a Harness), so the worst case is about 2 s + the budget + overhead, under the hook and Lambda timeouts (10 s each in our captures) |
| `SLASHID_SHADOW_MODE` | `false` | evaluate and log, answer allow |

`LOG_LEVEL` (unprefixed, default `INFO`) sets the Python log level; the lines to alert on are INFO.

The switches skip the check, apply before the format-change checks of section 3.2 rule 1, and a container whose surface is disabled writes one `pass_through` line at start; a flag change is a function update, not a re-attach, except that the attached Harness `failureMode` copies the fail mode and shadow setting (section 5), so changing those means re-running the attach recipe, which the README says. `SLASHID_INCLUDE_RAW_CONTENT`, inherited from `BaseConfig`, is forced off: connector files carry no text.

**Fail mode.** A check that gives no answer (a transport failure, a non-200, an unparsable body, the budget running out, or a Gateway call with no identity to send) takes the fail mode, on every check. A 200 is always a verdict, an empty deny list included. A fail-mode deny is applied like any other, with the reason "Your organization's policy check is unavailable." Allow is the default for the reason the Anthropic config gives: refusing to answer is self-inflicted downtime. Every no-answer, and every parse-failure deny, writes a structured `fail_mode` log line (surface, check, reason, the mode applied) that a customer can alert on, since a fail-open outage is otherwise silent; with the allow default, a format change on the result side disables result checks with only that line, and the README says to alert on it. When our Lambda itself errors or times out, AWS decides, not this setting: the Harness hook's `failureMode` is set by the attach recipe (section 5), and the Gateway's behavior is unknown (section 6), so "fail mode deny" is not promised for a Lambda error on that surface.

**Shadow mode.** Every check is still sent and evaluated, but a deny, a fail-mode deny included, is logged and answered as allow. The log line keeps both the verdict the server gave and the one answered. Like Anthropic, we cannot mark a preflight as shadow on the wire, so the server cannot tell it from an enforcing deployment.

Logs hold the surface, check, tool name, call id, the verdict actions (not the server's reason text, which can name files) and the fail reason, never request headers (the `Authorization` header is present when `passRequestHeaders` is on), never a caller-set baggage value (`baggage_unverified` logs the reason only), tool arguments or tool results. Only the `User-Agent` and `baggage` values are read from the headers; the `Authorization` header is never read. The new payload models hide their input in validation errors (`hide_input_in_errors`, which `codex/config.py` sets on its settings), so an exception cannot echo a result. Headers are read through a small model with a case-insensitive validator, not `dict.get`. Baggage is read from the `baggage` request header (so `passRequestHeaders` is needed), else from `params._meta.baggage`, as W3C baggage (properties after `;` dropped, values percent-decoded) and, like the `User-Agent`, bounded in length (256 characters) because the caller sets it.

## 4. Event fields

These are the AgentCore values; fields not listed keep their defaults.

| Field | Harness hooks | Gateway hooks |
| --- | --- | --- |
| `request_id` | `{sessionId}:{hookEventId}` | `{session_id}:{REQUEST_ID}:request` (call check) and `:result` (result check); without a session id, `{REQUEST_ID}:request` and `:result` |
| `timestamp` | when the handler runs | when the handler runs |
| `identity_details` | `agent_arn` = `harnessArn`; `principal_arn` = the execution role from `GetHarness` (section 4.2) | `gateway_arn` = the client context's `GATEWAY_ARN`; `principal_arn` = `awsPrincipalArn`, else the Gateway's own role from `GetGateway`; `agent_arn` built from baggage `harness.id` when verified (section 4.2) |
| `conversation_id` | `sessionId` | baggage `session.id`; null when the caller sends none (a direct IAM client) |
| `parsed_as` | `agentcore-harness-hook` | `agentcore-gateway-hook` |
| `user_agent` | none | the request's `User-Agent`, when present |
| `model` | `AIModel(id="unknown")` | `AIModel(id="unknown")` |
| `available_tools`, `available_tool_servers` | the called tool and its server | the called tool and its server |
| `requested_tool_uses` | call check only | call check only |
| `used_tools` | result check only | result check only |

The call's id (`tool_use_id`, in `requested_tool_uses` and `used_tools`) is the Harness `toolUseId` or the Gateway `REQUEST_ID`; that is how the server pairs a call's two checks. `request_id` identifies the hook event. The Harness `hookEventId` is expected to be unique per event (section 6), so the two checks of a call differ, and it is unique where `toolUseId` may not be: the provider generates it, it looked random in our captures (`tooluse_`, `toolu_`, `call_`, `chatcmpl-tool-`), but a provider that numbers its calls (`call_0` on every turn) would repeat it within a session. The `REQUEST_ID` is a UUID that is expected to be the same on the REQUEST and RESPONSE of a call (the findings show it for the HTTP shape; section 6 gates the Gateway pairing on it), hence the `:request` and `:result` suffixes. The session id comes from the caller-set baggage on the Gateway side. The agent's identity goes in `identity_details.agent_arn`, not in `available_agents` or `used_agent_ids`, which describe sub-agents.

### 4.1 Tools and files

- **Tool names.** For the tool and server identity only (connector recognition below uses the raw name), a Gateway tool name `<target>___<tool>` (Harness `toolType` `agentcore_gateway`, and every Gateway message) is rewritten to `mcp__<target>__<tool>` before `resolve_tool`, giving the tool, the server `<target>` and kind `mcp`; on the raw name it would give `_<tool>` and kind `runtime`. A Harness `remote_mcp` name (`<server>_<tool>`, one underscore) cannot be split without the server's name, but `toolType` says it is MCP, so it is rewritten to `mcp__MCP Tool Server__<name>`: the whole name stays the tool, on a placeholder server of kind `mcp` (not `builtin`, which would mislabel it as a local tool). Builtin and inline names are left as they are, so an inline function named `a__b` is read as server `a`, and a Gateway target whose name contains `__` is split wrongly (limits of the shared name parser).
- **Recognizing connector tools.** `connector_files` gets the tool name as the platform gave it, with no renaming and no matcher of ours. The shared matcher gains a rule for a connector server of any name: a name that ends in a tool name the existing connectors have, after nothing or any prefix ending in `_`, so `gdrive___read_file_content`, `mcp__gdrive__read_file_content` and a `remote_mcp` `gdrive_read_file_content` all match. The tool names are those of the claude.ai and Codex handlers, assumed to be the same on AgentCore: Drive `search_files`, `list_recent_files`, `read_file_content`, `get_file_metadata`, `download_file_content`, `copy_file`, `get_file_permissions` (the claude.ai connector's tool names; the stand-in implements neither of these two), Codex's `search`, `fetch`, and Microsoft 365 and SharePoint `read_resource`, `sharepoint_folder_search`, `get_drive_item`. A name can belong to several handlers (`search` and `fetch` are in Codex's Drive and SharePoint, `get_file_metadata` in claude.ai's and Codex's Drive), so the rule runs every handler that knows the name and returns every handler's files from `connector_files`, and the caller merges them with `finalize.merge_by_refs` (which `finalize` already applies, and the `tool_call` module applies to the files it builds): the union of refs per file, the entry with a hash winning, and the name from whichever entry has one. Each handler's argument and result models are the shape check, and they are tightened where today's are loose, so that an unrelated tool gives nothing: a file tool needs `{fileId: str}`; a Drive search entry needs an `id` and a `mimeType` (claude.ai) or `file_or_folder` (Codex), and a result without that shape gives no ref or name; `read_resource` needs a `file:///` URI whose first segment is a Graph drive id (`b!…`), so `file:///home/u/x.txt` gives nothing; a SharePoint tool needs both drive and item ids, or a Graph or `sourcedoc` URL. Any target is recognized, so a Box or Notion tool with the same name and the same strict shape is read as Drive and its `google/<id>` ref matches nothing, and a generic `search` or `fetch` costs a failed parse per handler. `copy_file` and `get_file_permissions` give the source file's reference from the arguments (so copying a tagged file is denied; this supersedes `2026-10-13-connector-file-refs-design.md`, which did not record `get_file_permissions` because it exposes no content), on the call check and the result check alike; the copy's new id is not tracked. `create_file` is not extracted: it carries the tool id and no `accessed_files`. `share_file`, `update_file` and `trash_file` take a `fileId` too and are not extracted either: v1 checks files that reach the model, and they change a file instead; they can be added the same way. Only the Drive shapes are proven here (section 1, Real Drive); the Microsoft 365 and SharePoint names and shapes are assumed from the claude.ai and Codex captures (section 6).
- **Call check.** `requested_tool_uses` carries the call, and `accessed_files` holds reference stubs from the arguments of a recognized call (`connector_refs` and the existing `connector_stub`, e.g. `google/<fileId>`).
- **Result check.** `used_tools` carries the call with its `is_error` (Harness: `toolResult.status` or `isError`; Gateway: `result.isError` or an `error`). `accessed_files` come from a successful result: references and names from a search or recent-files result, a reference from a metadata or read result, and a content hash only from `download_file_content`, since a `read_file_content` result is a re-rendering. A result over 64 KiB arrives with the whole `toolResult` replaced by `{truncated, preview}` (captured), so its `status` is not available as a field and the result is not parsed: `is_error` is unknown (sent as not an error, deliberately: the field has no third value), its references come from the cached input and it gives no hash. A result's payload is read from `structuredContent` when it has one and otherwise from the first text block, so a result with only one of the two still gives references; other content blocks give none.
- **Tool input in the result check.** Most extractors need the input (the `fileId`) and the output (the name, the hash). Gateway RESPONSE carries the whole request. Harness `after_tool_call` has no `toolInput` (none of the captured events did), so the Harness handler caches the tool input of allowed `before_tool_call`s and hands it to `connector_files` with the output, as the Gateway does with the request it carries; the cache also supplies the input when the result is truncated. Where the result names a file (an `id`) and the cached input names another, the result wins; a `read_file_content` result carries no `id`, so the cached `fileId` stands. On a miss (another or recycled container, likelier under parallel tool calls, which Lambda can run on separate containers) the check is built from the result alone and the miss is logged with the tool name and call id, at info level when `is_connector_tool` knows the name and at debug otherwise, since only calls with references are cached: a Drive read or metadata result is expected to repeat the file id (`id`, or in its `viewUrl`; section 6), and a tool whose result does not name the file gets no `accessed_files`.
- **Input cache.** A small module-level cache class (a dict of entries with an expiry, behind `has`, `get`, `put` and `pop`, so a resilient store can replace it later), keyed on `json.dumps([harnessArn, sessionId, toolUseId])` (one helper for `put` and `pop`, so a separator inside an id cannot join two keys and the same ids on two harnesses stay apart). The entry holds the tool name and the raw tool input, which the connector rules need whole; it stays in the container's memory and is never sent or logged. A persistent store later would hold the arguments, so it needs the protection of any store of tool arguments. A read checks that the tool name matches the call, and the entry is popped by its own `after_tool_call` before the own-deny shortcut (section 2) is taken, so a call denied downstream leaves no entry, and a provider that repeats an id across turns (`call_0`) does not collide; parallel calls in one turn carry distinct ids. It is written only when the answer is allow (a shadow-mode deny included) and the call check found at least one file reference, so other tools' arguments, such as `shell` commands, are never held, and the bound of 1000 entries stays small; a call denied by its own `before_tool_call` has no entry. `before_tool_call` puts it with a 10-minute expiry (wall-clock time) and `after_tool_call` pops it. Every `put` drops expired entries and, past 1000 entries, the oldest, so calls whose `after_tool_call` never arrives do not accumulate. The expiry and bound are constants of the package, not settings. A resilient store (DynamoDB or Redis) implements the same methods. The Gateway hooks need none.

### 4.2 Identity

`identity_details` carries both who the agent is and the identity it runs as, when each is available. This changes the shared `AWSIdentityDetails`:

- `principal_arn: str | None` (required today): the running identity, the role or user the calls are made with; for a Gateway call with no `awsPrincipalArn` (a JWT Gateway), the Gateway's own role, which is what its targets see.
- `agent_arn: str | None` (new): the AgentCore agent resource, the Harness ARN (a Runtime ARN, where one is known).
- `gateway_arn: str | None` (new): the Gateway that served the call, from the Lambda client context, where AWS sets it.
- At least one of the three must be set, the rule the Anthropic and OpenAI variants already apply (`_at_least_one_identifier`).

| Caller | `agent_arn` | `principal_arn` | `gateway_arn` |
| --- | --- | --- | --- |
| Harness, seen by Harness hooks | `harnessArn` from the payload | the execution role from `GetHarness`, cached; absent if the lookup fails | absent |
| Harness, seen by Gateway hooks | built from the baggage `harness.id`, with the account, region and partition of the Gateway ARN, only when verified (below) | `awsPrincipalArn` (the same role) | `GATEWAY_ARN` |
| Runtime agent, seen by Gateway hooks | absent: the baggage carries only `session.id` | `awsPrincipalArn` (the Runtime's role) | `GATEWAY_ARN` |
| Direct IAM client | absent | `awsPrincipalArn` (the user or role) | `GATEWAY_ARN` |
| Client of a JWT-authorized Gateway | absent: nothing to verify the baggage against | the Gateway's role from `GetGateway`; absent if the lookup fails (the token is not read, so every caller looks the same) | `GATEWAY_ARN` |

**Server change.** The server must accept `agent_arn` and `gateway_arn`, and a missing `principal_arn` when either is set; it is batched with the other server spec syncs. It ignores unknown fields today, so both can be sent first. Production returned 200 for `agent_arn` with `principal_arn` and for an identity with only `gateway_arn`; whether it resolves a gateway-only identity to anything is unconfirmed, and an `agent_arn` without `principal_arn` (a Harness event whose role lookup failed) was not sent (section 6). A missing `GetHarness` or `GetGateway` permission is logged as `role_lookup_failed` and the event goes without the role.

**Verifying the baggage.** The baggage is set by the caller, so a Harness id in it is a claim. The id must match the pattern of a harness id (`[a-zA-Z][a-zA-Z0-9_]{0,39}-[a-zA-Z0-9]{10}`, botocore's pattern for the `GetHarness` `harnessId`) before it goes into an ARN. The Gateway hooks rebuild the ARN from it and the `GATEWAY_ARN`'s partition, region and account, look its role up with `GetHarness` and set `agent_arn` only when that role equals `awsPrincipalArn`. With no `awsPrincipalArn` (a JWT Gateway), no `GATEWAY_ARN`, an invalid id, a failed lookup (a Harness in another account included) or a mismatch, `agent_arn` is left out and a `baggage_unverified` log line says why; the event still carries `gateway_arn` and any principal. The check shows that the claimed Harness runs with the caller's role, not that the caller is that Harness: another Harness or Runtime agent sharing the role can claim it, so the server should not treat a Gateway-side `agent_arn` as stronger than the role, and the README says so. `conversation_id` (baggage `session.id`) stays a claim, which the server should treat as one. Both Harness paths give the same pair when they can (section 6 asks whether the baggage `harness.id` rebuilds the `harnessArn`).

**Role lookup.** The Harness hooks' `principal_arn`, and the Gateway hooks' baggage check, come from `GetHarness` (`executionRoleArn`), called in the Lambda's own region (not the ARN's; the function is deployed in the region of its Harnesses and Gateways) and with the harness id taken from the `harnessArn` (its last segment), which needs `bedrock-agentcore:GetHarness` on the Lambda's role. The cache key is the `harnessArn`, stable across versions and per-invocation overrides (it never changed in the captured hook events), in a second instance of the same cache class. The Gateway hooks' baggage check uses a third, small one (100 entries, 60 s expiry, failures 30 s) so ids chosen by callers cannot evict the Harness hooks' entries, re-reads uncached once on a mismatch before dropping `agent_arn` (a former holder of the role can still claim the Harness for up to 60 s), and makes at most 10 uncached claimed-id lookups per container per minute, after which `agent_arn` is left out. The permission is `bedrock-agentcore:GetHarness` on `harness/*` of the account, and the response model keeps only `executionRoleArn`. **Gateway role.** A Gateway call with no `awsPrincipalArn` gets `principal_arn` from `GetGateway` (`roleArn`), with the Gateway id taken from the last segment of `GATEWAY_ARN`; it needs `bedrock-agentcore:GetGateway` on the Gateways the function serves (the template grants `gateway/*` of the account and region). The key is the Gateway ARN, which AWS sets and no caller chooses, so it shares the Harness hooks' cache instance (5 minutes, failures 30 seconds) and runs before the check's budget like the other lookups. A failed lookup leaves `principal_arn` out and logs `gateway_role_unavailable`; the event still carries `gateway_arn`. The role can change: `UpdateHarness` accepts a new `--execution-role-arn`, and we found no per-invocation role override. So the entry expires (5 minutes, a constant), and a changed role shows up on the Harness hooks after at most that long; on the Gateway hooks `principal_arn` is the current role on every call, and only the baggage check compares with a cached one. A failed lookup is cached briefly (30 seconds, a constant) so a missing permission does not add a call to every hook, and logs a `role_lookup_failed` line (the kind of lookup and a fixed error word, such as `access_denied`). The lookup runs before the check's budget starts and the server is told the full budget, so a cold container never shortens the server's time (which would turn a slow check into a server-side deny); if it fails or times out the event has no `principal_arn`, which is cached for 30 seconds like any failure; the event is still sent. The server's AssumeRole unrolling uses `access_key_id`, which no payload field supplies; the Gateway's SigV4 `Authorization` header carries one, and v1 does not read it.

### 4.3 Changes to `shared/`

- `AWSIdentityDetails`: `agent_arn` and `gateway_arn`, and `principal_arn` optional with the at-least-one rule (section 4.2).
- Result payload in `connector_files`: `tool_output` may be today's forms (a string, or a list of `{text}` blocks) or an MCP result object `{content, structuredContent}`. The Gateway adapter passes its `result` object; the Harness adapter passes the `content` list of its `toolResult`, which has no `structuredContent`. For an object with `structuredContent`, every handler (claude.ai's `_result` and Codex's `_payload`, Drive and SharePoint) takes it as the tool's JSON; otherwise `_result` takes the first text block's JSON as before and `_payload` the text envelope's `structuredContent` as before. The real Drive server sends both, the same JSON. The Harness result carries the content list only, so for Codex-shaped results, whose JSON travels in `structuredContent`, the Harness result check finds no references; the call check and the Gateway result check do.
- Connector matcher in `connector_files`: the any-server rule of section 4.1, tried only when no exact claude.ai or Codex pattern matched (an exact pattern with an action it does not know gives nothing), and `is_connector_tool(name)`, true when a handler knows the name. The connector rules are shared, so every forwarder that calls them gets the rule. The shape each handler requires, where today's models are all-optional:

  | Handler | Call needs | Result needs |
  | --- | --- | --- |
  | Drive `search_files`, `list_recent_files` (claude.ai) | nothing | entries with `id` and `mimeType` (folders skipped) |
  | Drive file tools (`read_file_content`, `get_file_metadata`, `download_file_content`, `copy_file`, `get_file_permissions`) | `{fileId: str}` | nothing more; the name is `title`, a hash only from `download_file_content` |
  | Codex Drive `search` | nothing | entries with `id` and `file_or_folder` |
  | Codex Drive `fetch` | a Drive-host URL | or a result `id` with `mimeType` or `file_or_folder` |
  | `read_resource` (Microsoft 365) | `file:///` URI whose first segment is a Graph drive id (`b!…`) | nothing more |
  | `sharepoint_folder_search` | nothing | blocks with `driveId` and `id` |
  | Codex SharePoint `search`, `get_drive_item`, `fetch` | `drive_id` and `item_id`, or a Graph URL, or a `sourcedoc` link on a Microsoft host | entries with `drive_id` and `item_id` |

  `_texts` also reads the `content` blocks of an MCP result object. Duplicate files from several handlers are merged by the caller (section 4.1). A test per handler feeds it a look-alike shape (section 5). In the Drive handler `list_recent_files` read like `search_files`, `copy_file` and `get_file_permissions` giving the source reference from the arguments, and a result-only path that takes the file id from a read or metadata result.
- A public builder from `ConnectorFile` to `AIAccessedFile` with hashes (`_build_accessed_file` is private today; `connector_stub` already builds the reference-only form), used by the result check.
- `join_deny_reasons` moves from the Anthropic hook (`anthropic/src/slashid_anthropic_forwarder/hook/preflight.py`) so both packages use it.
- `sink.preflight_invocation`: `PreflightError` carries a cause (transport error, timeout, status, unparseable), so the module can retry only a transport error (`httpx.TimeoutException` subclasses `TransportError`, so the timeout is classified first).

## 5. Attaching and testing

**Attaching.** v1 ships README recipes for both surfaces, no tooling. `UpdateHarness` replaces the whole hooks list, so the recipe is read, merge ours in, write; a deploy clears Harness hooks, so it is repeated after each. The recipe sets `timeoutSeconds` 10 on both hooks, `failureMode` on both hooks to match `SLASHID_VERDICT_FAIL_MODE`, and allow on both when shadow mode is on, since AWS applies `failureMode` to a Lambda error whatever the shadow setting says. A Gateway takes one REQUEST and one RESPONSE interceptor, with `passRequestHeaders` on (the README notes that this puts the caller's `Authorization` header into the Lambda payload; only `User-Agent` and `baggage` are read), and an `UpdateGateway` that omits `interceptorConfigurations` clears them (tested), so attaching, and every later gateway update, resend them. A Harness invokes its hooks with its execution role, not as the service (confirmed on a real Harness), so the function needs one resource-policy statement per Harness execution role (`HarnessRoleArns`); the Gateway only needs `lambda:InvokeFunction` for its role. Anyone else who can invoke the function can supply a client context and so forged identities, so the permissions are limited to those roles. Both are attached per resource, with no account-wide switch. Packaging and release follow `bedrock/` (a zip release and a CloudFormation template); the template, the resource policies and the release sequence belong to the implementation plan.

**Delivery.** Two pull requests, in order. The first (merged as PR 120) changes `shared/` (section 4.3: the identity model, the connector rule and result payload, the public file builder, `is_connector_tool`, the `PreflightError` cause) and moves `join_deny_reasons` out of `anthropic/`, with its own tests; it does change what existing forwarders send: the stricter connector models, the new Drive tools (`list_recent_files`, `copy_file`, `get_file_permissions`, the result-only id path) and the any-server rule reach every forwarder that calls `connector_files` or `connector_refs` (Bedrock, Vertex, Anthropic and Codex), so it carries look-alike negative tests per handler (`mcp__fs__read_resource` on `file:///home/u/x.txt`, a `web_search` returning `{results:[{id,title}]}`, a `fetch` of a non-Drive URL, another provider's `search_files` result without `mimeType`) and those changes are called out in its description. The existing claude.ai search fixture gains the `mimeType` the real server returns (the code already reads it to skip folders), and a real hit without one gives no ref. A later change (PR 121, merged) replaced `aioboto3` with `aiobotocore` in the workspace. The second adds `agent-core/` (the handler and its two adapters, the `tool_call` module, config, README recipes, packaging, the workspace member, `uv.lock`, and CI and release wiring) on top of it; its live tests need the server's `agent_arn` change, so it can merge before it can be validated end to end. Neither is merged without your approval.

**Testing.** Checks are tested against the real SlashID instance, not a stub, with the push token the Bedrock capture uses (`SLASHID_PUSH_TOKEN`, kept outside the repo). Three layers:
- Offline: handler-level tests over fixtures from the captures with ids replaced, and hand-built ones for what was not retained (inline and remote MCP tools, `hook_stopped`, a Policy `-32002` RESPONSE, a truncated result, a stale pooled connection that is retried once, a client older than 4 s that is replaced), with the SlashID call faked. It also covers: the own-deny reference (verifies; tampered text; a different key; a second block or `structuredContent`; trailing whitespace; a multi-byte reason at the 500-character cap); a JWT Gateway `tools/call` fixture; fail-mode, parse-failure and unrecognized-payload outcomes across `allow`, `deny` and shadow on both surfaces; baggage parsing (header over `_meta`, bad percent-encoding, the length cap) and the verification of section 4.2 (match, mismatch, no principal, failed lookup); Harness-versus-Gateway parity of tool id, server and file references for one call (Codex-shaped results excepted, section 4.3); the input cache (bounds, expiry, miss); the Gateway role fallback (an IAM call keeps `awsPrincipalArn`, a JWT call gets the Gateway's role, a failed lookup), the role caches (expiry, negative entries, eviction, the per-minute limit, a lookup that times out), rule 1's variants (another version, neither `mcp` nor `http`, an unknown Harness event, both discriminators, an absent `gatewayResponse`) and their answers, the `pass_through` and `fail_mode` lines, cache keys that repeat (`call_0`), a name mismatch on read and the own-deny pop, an allow echo that keeps unknown fields, and a log-leak test that no exception path logs a payload, header, baggage value or file name. PR 1 adds the at-least-one rule and a check that the Bedrock wire bytes do not change when `principal_arn` becomes optional. The baggage "match" case cannot prove the ARN rebuild offline (the id is synthetic), so the live layer carries it.
- Live against SlashID: the same fixtures through the handlers locally, which also confirms the server accepts a tool-only preflight with an unknown model and no `event_type`; then in the demo account: a tagged Drive file is denied by both surfaces, result-side redaction holds for search snippets, and fail mode, budget and shadow mode behave as configured; a real Harness-to-Gateway call whose Gateway-side `agent_arn` equals the `harnessArn` the Harness hook saw; the deny reference through each hop, a large `tools/list` echo, and an `isError` true replacement (section 6). The latency of both handlers with a real round trip is recorded in the findings (section 13): about 170-195 ms per warm check, 875 ms for the first check of a cold container.
- The live layer needs the token, so it is opt-in and skipped in CI. The server records preflights, so live runs use the test tenant and ids that are clearly synthetic.
